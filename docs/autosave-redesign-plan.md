# 自動保存の再設計プラン

最終更新: 2026-09-30 / ステータス: 段階 1〜4 を実装済み（段階 3・4 は実機で未確認）

## 背景

作業が長くなるほど動作が重くなり、自動保存が止まる、または再読み込みでインクが消える不具合が報告された。
調査では個別の不具合が多数見つかり、部分修正を重ねたが、根本解決に至っていない。

## 調査で分かった事実

### 保存が止まる・重くなる
- 保存の書き込みにタイムアウトがなく、1回詰まると以降の保存が無言で止まる（修正済み）。
- 保存のたびに、文書内の全ラスタを IndexedDB から読み直していた（キャッシュで緩和済み）。
- 取り消し履歴が、ページ全体サイズのキャンバスをそのまま最大 50 手（設定上限 200）持つ。約 8MB × 50 手。
- エンコード失敗・破棄時に完了通知が出ず、「エンコード中」が消えなくなる（修正済み）。
- 画面遷移や `pagehide` で DB 接続を閉じたあと、編集画面が閉じた接続を持ち続けて全保存が失敗する（修正済み）。
- 全ページ表示時に約 62 枚の大きなキャンバスがメモリに載り、iPad でエンコードが失敗する（未対応）。
- 非表示・再試行のたびに、全ラスタを「変更あり」として書き直している（`useEditorController.ts` の `collectRasterIds(present)`）。

### インクが消える
- 未エンコードのストロークを持つキャンバスが LRU 退避で捨てられる（修正済み）。
- 未デコード（空白）のキャンバスに対する結合・貼り付けで、インクが失われる（修正済み）。
- 選択ツールの範囲切り出しが、ページのインクをクリップに移す。クリップに気づかず削除してゴミ箱を空にすると、インクが文書から消える。
- 「ゴミ箱を空にする」は文書の参照を消すだけで、IndexedDB の PNG は消えない（表示は「完全に削除」）。起動 GC も、作品が存在しない場合しか消さない（容量の増加、および復元できた理由）。

## 構造上の根本原因

ライブの書き込み自体は、既に 1 トランザクションになっている（`commitDocumentGeneration` / `putLiveAtomic`）。
途中の状態が保存されるのは、書き込みではなく「何を書くかを集める側」の問題である。

| 構造上の問題 | 実際に起きたこと |
|---|---|
| 変更ありのラスタに PNG が無くても、文書だけコミットする | クリップは消えているのにページにインクが無い、など |
| エンコード待ちを 15 秒で打ち切り、そのままコミットする | 同上 |
| エンコードに失敗したラスタは、古い PNG のままコミットが通る | 同上 |
| 文書の状態と、ラスタの画素の版を結びつけるものがない | どの PNG がどの文書に対応するか、保存後に確かめられない |
| ラスタの実体が 3 か所にある（キャンバス、`encodedPng`、IndexedDB）。状態をフラグや世代番号で追っている | 「エンコード中」が残る、空のキャンバスを使う |
| 取り消し履歴と全ページ表示が、ページ全体大のキャンバスを大量に持つ | 作業が進むほど重くなる、iPad でエンコードが失敗する |
| 削除や整理の仕組みがない | 容量の増加 |

## 進め方

| 段階 | 内容 | スキーマ変更 |
|---|---|---|
| 1 | コミットのゲートと、変更ありの判定の修正 | なし |
| 2 | 取り消しの矩形化、全ページ表示の縮小 | なし |
| 3 | 既存ストアを流用したリビジョン化（K=2、コミット時 GC） | `DB_VERSION` を上げる |
| 4 | 保存パイプラインを状態機械に整理 | なし |
| 5 | タイル化 | 段階 2 の計測後に判断 |

### 段階 1: コミットのゲートと、変更ありの判定
- 変更ありのラスタのうち、文書が参照しているものに、エンコード中・エンコード失敗・PNG なしが 1 つでもあれば、コミットしない。ジョブは残し、失敗として画面に出す。
- エンコードが完了したら、残っているジョブを自動で再実行する。
- 最後にコミットした PNG と同じものは書かない。呼び出し側が全ラスタを渡しても、実際に変わったものだけ書く。

### 段階 2: メモリ（実装済み）
- ペンと消しゴムの取り消しは、ストロークの外接矩形の画素だけを持つ。切り出し・結合・全消去は、従来どおりラスタ全体を持つ。
- ページ全体大のキャンバスを持つラスタは、固定 8 枚（画面内を優先）と、それ以外の直近 8 枚までにする。
- それ以外の表示中ラスタは、表示サイズに縮小したプレビューで描く。編集を始めた時点で、PNG を同期デコードしてキャンバスに戻す。
- 同期デコードにより、デコード完了前の編集でインクが消える経路（ペン、消しゴム、切り出し、結合、取り消し）を塞ぐ。
- 残り: iPad 実機で、メモリと保存時間、全ページ表示での描き始めの引っかかりを計測する。

### 段階 3: リビジョン化（実装済み）
- 新しいストアは作らない。`rasters` ストアをそのまま使う。
  - 既存のキー `rasterId` を「リビジョン 0」とみなす。
  - 新しい書き込みは `rasterId@世代番号` とし、一度書いたら変更しない。
- 文書 JSON に `generation` と `rasterRevs`（ラスタごとの参照リビジョン）を持つ。この 2 つは保存側が決め、編集側から渡された値は使わない。
- `documents` を最新の世代、`documentSnapshots` を 1 つ前の世代とする（K=2）。`rasterSnapshots` は読み取り専用になった（移行前の予備を開くときだけ使う）。
- 保存は 1 トランザクション。最新と 1 つ前の文書を読み、新しいリビジョン、新しい文書、1 つ前の文書、メタを書き、2 世代より前のリビジョンを削除する。途中で失敗すれば全体が取り消される。
- PNG でないデータは保存を拒否する。
- 保存するラスタは、「保存済みと分かっている PNG と違うもの」すべて。変更ありの印には頼らない（取り消しで戻ったクリップも書く）。起動直後は、読み込んだ PNG とバイト列が同じものを保存済みとみなす。
- 起動時 GC は、最新にも 1 つ前にも使われていないリビジョンだけを消す。GC が読んだ世代より新しいリビジョンは消さない（保存と競合しても安全）。
- 移行前のキー（リビジョン 0）は、GC でも保存でも消さない。`{projectId}:pdf` も同じ。
- `DB_VERSION` は 3。古い版のアプリは、この DB を開けない。
- 書き出し・LAN 転送・複製・一覧サムネは、リビジョンを解決して読む。パックの文書にはリビジョンを含めない。

#### 段階 3 で見送ったもの
- 複数タブの排他（`navigator.locks`）。Safari でロックが残って作品を開けなくなる場合を、実機なしで確かめられないため。
- 移行前のキーと `rasterSnapshots` の掃除。作品 1 つにつき、最大で作品 2 つ分の古いデータが残る。`?recover=` がこのキーを使うので、消す時期は別に決める。

### 段階 4: 保存の待ち方の整理（実装済み）
- 自動保存側の状態を 2 つにまとめた。
  - ラスタごとの状態: エンコード中、またはエンコード失敗。
  - 文書が必要とするラスタの集合: 文書の変更と一緒に画素が変わったラスタ（切り出し、焼き込み、結合、複製、取り消し・やり直し）。
- 文書を保存できないのは、「文書が必要とするラスタ」にエンコード中・失敗のものがある間だけ。
- 通常のストロークと消しゴムは、文書が必要とするラスタに入らない。エンコード中でも失敗でも、他の保存は進む。失敗は表示に出る。
- 保存は、実行中のエンコードを最大 15 秒待って一緒に書く。それを過ぎたら、文書が必要としていない限り先に進む。
- 取り消し・やり直しでは、戻したラスタのエンコードをその場で始める。以前はアイドル時まで始まらず、文書だけが先に保存されていた。

#### 段階 4 で見送ったもの
- エンジン内部の管理（`pendingEncodes`、`pendingEncodeIds`、`encodeGeneration`、`hotRevision` など）の一本化。挙動は変わらない作り替えで、実機の試験なしに触る利点が小さい。

### 段階 5: タイル化
- 256px タイルは、1 作品でマニフェストが約 2,000 件になり、保存量が変更範囲に比例する利点を損なう。
- 段階 2 の計測で足りない場合にだけ、タイルの大きさを含めて検討する。

## ページを閉じるとき
- 破損を避けるための特別な処理は、段階 1 のゲートで不要になる。
- 最後のコミット以降の変更を書く処理は残す。エンコード済みのものだけを 1 トランザクションで書く。

## 複数タブ
- 作品ごとに `navigator.locks` を編集中ずっと保持する。2 つ目のタブは、その作品を編集用に開かせない。
- 書き込みの直列化だけでは、後から書いたタブが勝つ問題が残るため。

## 復旧
- 直近 2 世代は、保存の途中で落ちた場合の保険である。保存は 800ms ごとに走るので、誤操作からの復旧には使えない。
- 段階 3 の GC を入れると、`?recover=` で PNG を拾える状態がなくなる。
- 誤操作からの復旧が必要なら、編集開始時の世代を 1 つ固定で残す。段階 3 の着手時に決める。

## 検証方針
- fake-indexeddb で、保存の各段階に障害を注入する。どの時点で落ちても、起動時に整合した世代が得られることを確かめる。
- 容量超過（`QuotaExceededError`）の注入を加える。
- fake-indexeddb は Safari 固有の挙動を再現しない。次は iPad 実機で確かめる。
  - 62 ページの作品で、描画・切り出し・非表示・再読み込みを繰り返し、インクが残ること。
  - `pagehide` 直後の再読み込みで、直前の保存状態が開くこと。
  - 長時間の作業で、使用容量が増え続けないこと（段階 3 以降）。
- 段階 3 では、旧データからの移行を実データに近い形で試験する。

## 未決事項
- 編集開始時の世代を固定で残すか（段階 3 の着手時）。
- 選択ツールの範囲切り出しの UX（通知の表示、「インク」対象の既定値）。保存の再設計とは別に決める。

## 関連する既存の修正（`fix/autosave-stall` ブランチ）
- 保存にタイムアウト・失敗表示・再試行・書き出し導線を追加。
- エンコード失敗の再試行と、破棄時の通知。
- 保存時に検証済みラスタを再読み込みしないキャッシュ。
- 自動保存が閉じた DB 接続を持ち続ける問題の修正。
- 未エンコードのキャンバスを LRU 退避しない。
- PNG エンコードの同時実行を 2 件に制限。
- エンコード中は保存を待ち、ページを閉じるときの書き込みを一括にする。
- 未デコードのキャンバスに対する結合・貼り付けを待つ。
- 削除されたクリップの復元（`?recover=`）と、調査用ログ。
